# ThisOS design

This document describes what ThisOS is and how its parts fit together. It covers what is decided and what the next milestone needs, not the whole system in advance. How code is written, tested and reviewed is in [CONTRIBUTING.md](../CONTRIBUTING.md). Decisions that are hard to reverse have a short record in [adr/](adr/).

## Goals

ThisOS is a general-purpose operating system written in Rust, built on a microkernel. Safety means three things here:

- The kernel is memory-safe Rust. Its unsafe code sits in one crate per architecture, documented and tested.
- Programs are isolated by the hardware: each runs in its own address space in user mode.
- No program has ambient authority. A program can reach only the kernel objects it holds handles to, and a new program starts with only the handles its creator gives it.

ThisOS is not Unix-like and has no libc. Programs target Rust's standard library once it is ported (milestone 7); until then they use `no_std`, `alloc` and the ThisOS runtime crate.

## Non-goals for now

These are deferred. Each comes back through a decision round when a milestone needs it.

- More than one CPU core on aarch64, until there is aarch64 hardware to test it on ([0006](adr/0006-aarch64-behind-x86_64.md)). x86_64 gains SMP in the milestone before milestone 5 (see Milestones).
- riscv64 bring-up, and aarch64 beyond QEMU or past what a decision round schedules ([0006](adr/0006-aarch64-behind-x86_64.md))
- The IOMMU
- Networking and USB
- Image signing, Secure Boot support, updates and packages
- Resource quotas and accounting
- Hardening against speculative-execution side channels beyond what the CPU and firmware do by default
- An interface definition language for IPC
- Vendoring dependencies or recording their publishers

## Architectures and hardware

ThisOS is 64-bit only. Architecture names follow Rust's `target_arch`.

- **x86_64** is the main architecture. It runs in QEMU and on real hardware, and both must pass the same tests.
- **aarch64** runs in QEMU only, behind x86_64 ([0006](adr/0006-aarch64-behind-x86_64.md)): work items land on x86_64 first, and aarch64 gains a feature when a decision round schedules its port. It has milestone 4's parity, but for a serial port, and passes the same QEMU tests.
- **riscv64** is a long-term target, to be tested in QEMU only. No code for it exists yet.

QEMU runs the q35 machine with OVMF firmware and is to emulate the same devices as the test laptop: an NVMe disk and an i8042 keyboard, with no virtio. One driver per device class then serves both. Today it has the image as USB storage on an xHCI controller, the way the laptop boots its stick, and no NVMe disk, which comes with the NVMe driver. QEMU runs without `-nodefaults`, so q35 also adds an e1000e NIC and VGA, which no driver uses.

The real-hardware target is a Lenovo 83DA laptop:

- Core Ultra 5 125H (Meteor Lake, 18 threads, mixed P- and E-cores)
- UEFI only
- NVMe SSD and an i8042 keyboard
- VT-d with interrupt remapping
- Wi-Fi only, no serial port

Unsigned images need Secure Boot turned off in its firmware settings.

## Boot

The kernel boots through UEFI only, using the `bootloader` crate (0.11) unforked. The kernel is an ELF built for `x86_64-unknown-none`. `bootloader` maps all of physical memory at an offset it picks, and the kernel reaches any frame through that mapping. The kernel is position-independent, and the loader puts it, its stack, the boot information, the framebuffer and the physical-memory mapping in the upper half of the address space, from `0xffff_8000_0000_0000`, which leaves the lower half to user space. The lower half holds only the loader's own identity mappings, which the kernel drops when it switches to its own page tables. Its ramdisk is a ustar archive of the user programs (see User mode).

`bootloader` supports only x86_64. The arch crate converts its `BootInfo` into the kernel's own boot structure in one place, so a different loader for another architecture changes one file.

aarch64 boots through Limine 12.9.6 under edk2. The kernel is an ELF built for `aarch64-unknown-none-softfloat`, linked statically at `0xffff_ffff_8000_0000` by a linker script that `kernel/build.rs` passes for aarch64 alone. xtask writes a GPT disk with one FAT partition holding Limine's `BOOTAA64.EFI`, its configuration, the kernel, the ramdisk, which Limine loads as a module, and the build ID. Limine maps physical memory in the upper half and enters at EL1 on a stack of its own; `_start` moves to SP_EL1 on a boot stack in the kernel's image. The arch crate builds `BootInfo` from Limine's answers, and reads the device tree Limine passes on, which edk2 hands over only when QEMU runs with `acpi=off`.

## Crates

```
ThisOS/
  Cargo.toml          workspace for target crates
  .cargo/config.toml  default target x86_64-unknown-none
  kernel/             thisos-kernel: the kernel, a library and a thin binary, generic
  hal/                thisos-hal: traits the kernel needs from an architecture
  arch/x86_64/        thisos-arch-x86_64: implements thisos-hal
  arch/aarch64/       thisos-arch-aarch64: implements thisos-hal under QEMU's virt machine
  abi/                thisos-abi: syscall numbers, errors, handle and rights types
  lib/*/              host-testable no_std logic
  user/rt/            thisos-rt: user runtime (entry, syscalls, allocator, panic)
  user/init/          the first process
  xtask/              a separate workspace: image building, QEMU, tests, font
```

Dependencies point from specific crates to generic ones. `thisos-kernel` depends on `thisos-hal`, and, under `cfg(target_arch = ...)`, on the architecture's crate, `thisos-arch-x86_64` or `thisos-arch-aarch64`, which also depends on `thisos-hal`. The kernel reaches the hardware only through the `thisos-hal` traits and never names an architecture's types. `thisos-arch-x86_64` is the only crate that may depend on the `x86_64` crate, and `thisos-arch-aarch64` the only one that may depend on `aarch64-cpu` and `limine`, so architecture code leaking into generic crates shows up as a dependency change.

All crates are named with the `thisos-` prefix. A new crate is added only when its dependencies, unsafe status or test environment differ from its neighbors'; otherwise the code is a module.

## Kernel

The kernel owns these mechanisms ([0001](adr/0001-kernel-scope.md)):

- physical memory, page tables and a kernel heap
- threads and a preemptive scheduler
- handles and the kernel objects they name
- IPC channels and shared memory
- delivery of interrupts to user space

Drivers, filesystems and networking run in user space. Something moves out of the kernel only when there is evidence for it.

The kernel hands out physical memory in 4 KiB frames from a bitmap allocator in `lib/frames`, one bit per frame, scanned from the lowest word that may have a free one. It seeds the allocator once from the Usable regions of the loader's memory map, which the arch crate passes in `thisos_hal::BootInfo` as an iterator of regions of three kinds: Usable; Loader, which holds the kernel image, its stack, the loader's page tables and the boot information, the map included; and Firmware, with the firmware's own type. The bitmap is a 2 MiB static in the kernel's `.bss`, so it needs no memory before there is any to allocate. It covers physical addresses up to 64 GiB, and the kernel logs any usable memory above that as ignored. Frames below 1 MiB are never handed out: they hold frame 0 and the real-mode memory that starting another core needs. Loader regions stay in use: nothing reclaims them, since the memory they hold is small. An allocated frame is a `Frame`, which is neither `Copy` nor `Clone`; freeing one takes it, dropping one leaks its frame, and freeing a free frame panics. Trap handlers never allocate frames, because the allocator's lock is a spin lock.

The kernel runs on page tables of its own from early in `kernel::init`. The arch crate builds them from frames the allocator gives it: it copies every leaf of the loader's upper half, at its page size and with its flags, into new tables, adding the global bit, then loads CR3. Every address the kernel uses keeps its frame, and the lower half is left empty. It reserves one upper-half level 4 entry the loader left free, 512 GiB, and gives it its level 3 table at once, so that no upper-half level 4 entry changes after boot. The first 64 GiB of it are the heap's, the next 384 GiB the stacks', and the top 64 GiB kernel space, where the kernel maps its own memory through `thisos_hal::PageTables`: one 4 KiB page at a time, always no-execute and global, to a `Frame` the tables hold until `unmap` hands it back. A kernel-space address is never mapped again after it is unmapped, so code still using it faults instead of reaching other memory. `PageTables::map_stack` maps stacks in their window, one after another, each with an unmapped page below it that an overflow runs into and its start aligned to twice its size, and `map` and `unmap` refuse the whole window, so nothing maps a guard page. It returns a `PageTables::Stack`, which only the arch crate makes and which isn't `Clone`, and `unmap_stack` takes it back; when the frames or the window run out it returns `None`, having freed the pages it mapped, so a syscall that starts a thread fails instead of the kernel. Stack addresses aren't reused either, nor those of a stack that failed, and a 64 KiB stack takes 128 KiB of them, so the window holds about 3.1 million stacks a boot. A page-table entry keeps only a frame's address, so the arch crate takes a mapped `Frame` apart with `Frame::into_start` and makes it again with the unsafe `Frame::reclaim` when the entry goes; that function is why `lib/frames` denies unsafe code instead of forbidding it.

Each user address space is a level 4 table of its own whose upper half is a copy of the kernel's level 4 entries, so it shares every kernel table below them. `PageTables::new_space` makes one, as a `thisos_hal::AddressSpace`, which maps 4 KiB pages in the lower half above its first 64 KiB, so that a null pointer plus a small offset always faults, and below its last page, so that SYSRET always returns to a canonical address ([0007](adr/0007-syscall-abi-x86_64.md)). A user page is read-only, read-write or read-execute, and never writable and executable at once. As in kernel space, the space holds each mapped frame until `unmap` hands it back. Tables that `unmap` leaves empty stay until the space is destroyed: `destroy` hands back every frame still mapped through one callback and the frames of its tables through another, after loading the kernel's own tables if the CPU was using the space. Switching spaces loads CR3, which flushes the TLB but for the kernel's global pages, and is skipped when CR3 already holds the space; there are no PCIDs. The arch crate turns on SMEP and SMAP when it takes the page tables, and the kernel panics at boot on a CPU without them, before it loads the IDT, so the kernel can neither run user code nor read or write user pages but through code that sets RFLAGS.AC for it. Interrupt gates leave AC as it was, so every trap stub clears it with `clac`, and the handler runs with user access blocked; `iretq` gives the trapped code its AC back. New table frames are zeroed before they are linked in; mapped frames keep what they held. Page tables are never reached through a Rust reference, because the CPU's page walker sets Accessed and Dirty bits in them at any time, which Rust's aliasing rules don't allow while a `&mut` to the table lives. The arch crate reads and writes them through raw pointers into the physical-memory mapping, one atomic load, store or compare-exchange per entry; the PAT setup at boot uses the same code. Host tests run it under Miri over a buffer standing in for physical memory, with a fake CPU per test thread that holds CR3, records flushed pages and reports interrupts off; one test runs a second thread as the page walker, setting Accessed and Dirty bits while the test changes and clears entries. `take` and `grow_heap` run only in QEMU. The kernel holds its page tables behind a spin lock, which trap handlers never take.

The kernel heap is a `talc` allocator in the arch crate, the global allocator behind `alloc`'s boxes and collections, under a `spin` lock. Its memory is the bottom of the heap's 64 GiB, which only `PageTables::grow_heap` maps: each call maps one frame, writable and no-execute, at the page after the last, and extends talc's heap over it. `kernel::init` maps a fixed 4 MiB right after the page tables, and an allocation that doesn't fit fails, which panics through `alloc`'s error handler; growth on demand waits until something needs more. Every allocation a syscall reaches is fallible, a vector's `try_reserve` or `Arc::try_new`, for which the kernel turns on the nightly feature `allocator_ext`, so a full heap fails the syscall with `Error::NoMemory` and doesn't panic the kernel. One process can still fill the heap and make other processes' syscalls fail that way, since there are no quotas. Talc's counters are on, and `Platform::heap_stats` reads the bytes allocated and claimed, for the log line at boot and for tests that check nothing leaks. Trap handlers never allocate, because the heap's lock is a spin lock. `grow_heap` takes the frame and heap locks inside the page-table lock, and allocating takes the heap's lock alone, so the order has no cycle. Growth on demand therefore can't run from talc's out-of-memory path, which holds the heap's lock: `grow_heap` would take it again and spin forever.

The kernel logs through the `log` facade to two places: the serial port (COM1), which QEMU tests read, and a framebuffer text console, which is all the laptop has. The console uses JetBrains Mono rasterized to printable ASCII at 12, 16, 24 and 32 pixels per em, which give cells of 7×16, 10×22, 14×32 and 19×43 pixels. It uses the largest size that gives at least 40 rows, or the smallest when none does: 12 px on QEMU's 1280×800 screen (50 rows), 16 px on 1080p and on the test laptop's 1920×1200 (49 and 54 rows), and 32 px at 4K (50 rows). It keeps the text in a grid of cells and, when it scrolls, redraws from that only the cells whose character or color changes, because the firmware maps the framebuffer uncached: reading it is slow, and every store is a bus transaction. It writes two pixels per 8-byte store where the pair is 8-byte aligned, and a pixel alone where it isn't. Every record starts with the index of the CPU that logged it, as `0 INFO thisos_kernel::timer: ...` on both sinks, and the ring keeps the index in each record's header. Above the log, the first rows of the console's grid hold one 32-column status cell per CPU, packed several to a row: the CPU, the ticks it has drawn, the running thread, whether it runs the kernel or user code or idles, and the innermost lock it holds, or the lock it spins on in yellow. Each CPU redraws its own cell on every tick and when a lock spin passes 10 ms, only the characters that changed, through a third framebuffer handle and with no lock, so a hung CPU's cell shows where it stopped. It draws through `thisos_hal::Pixels`, whose stores take `&self`, which the arch crate implements over the framebuffer's raw pointer with volatile stores: no Rust reference to the framebuffer exists, since the loader's mapping of all physical memory maps it a second time. On the test laptop, redrawing the whole screen with one store per byte took 1.34 s. On x86_64 the arch crate also maps the framebuffer write-combining, so that the CPU gathers its stores into bursts: it changes PAT entry 1 from WT to WC and selects it on the framebuffer's pages. It does so only when the MTRRs make the whole framebuffer UC, because the loader's mapping of all physical memory is a second mapping of it, and a WC page must not also be mapped cacheable. `BootInfo` says whether it did, and the kernel logs it.

A kernel panic turns interrupts off first, so that no tick switches to another thread during the report, where a second panic would halt before the first is out. It then prints its message, its location and a backtrace that follows frame pointers to both log sinks, and halts every core. A trap the kernel reports as a panic goes the same way. The kernel is built with frame pointers for this. The backtrace stays inside the kernel stack and stops after 32 frames. Its addresses are link addresses, one byte into each call, so `addr2line -e` on the kernel ELF names them directly; the kernel holds no symbols. `core` comes prebuilt without forced frame pointers, so a frame inside it can be missing or end the walk early. A panic that finds the logger locked came from inside the logger, where the console may be half updated, and one before `logger::init` finds no sinks at all. Either way the report goes to panic sinks instead: a second handle on the serial port, and a second console on a second framebuffer handle, which the arch crate takes from the loader before it loads the IDT. Attaching that console clears the screen, so the log lines on it are lost, but the report and the test summary reach the laptop's screen. A panic during the report halts at once. In a test build a panic ends the test run on a summary of the results, then exits QEMU with a failure code, or halts on real hardware.

The arch crate loads its own GDT, TSS and IDT before the kernel's main function runs. The GDT holds, in this order, the kernel's code and data segments, the user data and 64-bit code segments, and the TSS, which is the order SYSCALL and SYSRET need; there is no 32-bit user code. SS, DS, ES, FS and GS hold the null selector in the kernel. Every trap enters through an assembly stub that saves the general registers, the vector and the error code in one trap frame, then calls the handler the kernel passed to `entry!` with the frame and a `thisos_hal::Trap` decoded from the vector. When the handler returns, the trapped code resumes; after a double fault or a machine check the arch halts instead, except after a double fault the handler abandoned to a test's recovery point (CONTRIBUTING.md, Tests). Double faults, NMIs, machine checks and debug exceptions run on 20 KiB stacks of their own, so a kernel stack overflow, which runs into the loader's unmapped guard page below the stack, still reaches the handler as a double fault, and a debug exception raised on the SYSCALL stub's first instruction, which a data breakpoint on a MOV SS before the SYSCALL would do, doesn't run on the user's stack. Those stacks start as statics with nothing unmapped below them; right after the kernel's page tables load, `Platform::move_trap_stacks` moves them to stacks from `map_stack`, which the arch keeps for good, so that an overflow of one faults instead of running into the memory below. The arch writes each stack slot of the TSS with one 8-byte atomic store, so that an NMI never finds half an address there: it keeps the packed TSS 4 bytes into an 8-aligned block, which puts the slots on 8-byte boundaries. A trap that user code raised goes to the user-mode handler (see User mode). Otherwise the kernel's handler returns from a breakpoint, counts a tick and switches threads on a timer interrupt, and panics on any other trap. That report has the trap, every register and a backtrace that starts at the trapped instruction. It goes through the panic handler's path and not through `panic!`, whose backtrace would start in the handler, and on a trap's own stack stop there.

Every one of the 256 vectors has a stub, and all but nine have an IDT entry, so an interrupt the kernel never asked for reaches the handler as `Trap::Stray` with its vector, and the kernel reports it as a panic. The APIC's spurious vector, 0xff, is the exception: it reaches the handler as `Trap::Spurious`, which the kernel ignores, as it does the GIC's spurious interrupt ID 1023 on aarch64, since an interrupt that went away before the CPU took it is no bug. Neither takes an end of interrupt. The nine are 9, 15, 22-27 and 31, which the CPU never raises and the `x86_64` crate's IDT doesn't let the arch set; an interrupt on one of them arrives as a general-protection fault naming its entry. The arch crate remaps both legacy 8259 PICs to vectors 0x20-0x2f, so that a stray line can't pass for an exception, and masks every line. The timer is the local APIC's, in x2APIC mode: its registers are MSRs, so it needs no MMIO mapping, and it works whichever mode the firmware left the APIC in. The kernel panics at boot on a CPU without x2APIC. It runs periodically at 100 Hz on vector 0x30, with the spurious vector at 0xff, and the arch crate sends EOI before it calls the handler, which may switch to another thread that runs for many ticks before this handler returns. Its frequency is the crystal frequency from CPUID leaf 0x15 when the CPU reports one there. Otherwise the arch crate measures it against PIT channel 2 over 50 ms. QEMU reports none, so it always measures, and gets about 1 GHz. The test laptop reports 38.4 MHz, and its PIT never counts, most likely because the firmware gates it; Linux on the same laptop finds the HPET dysfunctional too and uses the TSC. A test checks the reported frequency against a 50 ms count of the TSC, whose frequency comes from the same leaf (the crystal frequency times EBX / EAX), to within 5%. That shows the timer runs on the crystal, which is what the kernel relies on, though not that the crystal frequency itself is right. The PIT, waited on for at most 2^32 TSC cycles, is only the fallback for CPUs that report no frequency. The kernel logs the rate, the frequency and its source. `kernel::init` starts the timer and turns interrupts on as its last step, for every entry point.

Kernel locks are ranked spin locks from `lib/locks` (CONTRIBUTING.md, Locks). Each CPU keeps the list of locks held on it, at most 8, which belongs to the running thread: a thread switch saves the list into the thread that leaves and loads the arriving thread's, with the lock it was spinning for, and an interrupt handler's locks go on the interrupted thread's list and come off before it returns. Debug builds check every `lock()` against the list's ranks. In every build, spinning for a lock more than a second panics, naming the lock, the spinning CPU and thread, the holder's CPU and thread, and the holder's list when the holder is running. The second is counted on the TSC on x86_64, whose frequency comes from CPUID leaf 0x15 or, where the leaf gives none, as under QEMU's TCG, a measurement against PIT channel 2 at boot, and on `CNTVCT_EL0` at `CNTFRQ_EL0` on aarch64. Until the frequency is known, or where neither source gives one, spins have no limit, and the kernel logs which it is at boot.

The kernel runs threads, preemptively and round robin: every timer tick hands the CPU to the next ready thread, so one that never yields still gets preempted, even holding the frame, page-table or heap lock, and a thread that wants such a lock spins out its slice. The kernel's main function and the tests run in the boot thread, on the boot stack: the loader's on x86_64, one in the kernel's image on aarch64. Every other thread has a 64 KiB stack from `map_stack` with a guard page below it; aarch64's trap entries need that size. An idle thread runs only when no thread is ready, halting between interrupts with interrupts on, and the kernel's main function ends by exiting into it. A thread is running, ready, blocked or dead, and a yield with nothing else ready returns at once. Every thread has a 64-bit id from a counter, never reused, so a stale id names nothing. `thread::park` blocks the running thread until `thread::unpark` names its id, and `park_until` also until the tick count reaches a deadline; `sleep` parks until a deadline. A thread that an unpark names while it isn't parked keeps a wake, and its next park returns at once, so a wake that comes between a waiter's check and its park isn't lost. A park may return with neither, and callers check their condition again, as with `std::thread::park`. Objects that threads wait on keep their waiters' ids, not the threads. Blocked threads stay in the scheduler in a vector kept in order of id, which unpark and park search by bisection, and each tick readies the ones whose deadline has passed, in one pass over the vector, before it switches, so a deadline has the tick's 10 ms resolution. User code blocks only through the wait call, below. The arch crate's context switch is the same for a tick, a yield and an exit, through two HAL calls: `Platform::new_context(stack, entry)` makes a `Platform::Context`, a move-only token for a suspended thread that takes the `Stack` and holds it, and `Platform::switch(to)` suspends the caller, resumes `to`, and, when the caller runs again, returns the context of the thread that switched back to it, which the scheduler then files. On x86_64 the switch also keeps DS, ES, FS and GS per thread, null for a new one, since ring 3 can load them and would otherwise read what another process left there; aarch64 keeps `TPIDR_EL0` for the same reason. So no reference into the scheduler lives across a switch, and its lock, a spin lock held only with interrupts off, is released before one. A tick switches inside the trap handler: the preempted thread's trap frame stays on its own stack, and it leaves the handler when it next runs. Nothing allocates or frees under the scheduler's lock, since a preempted thread may hold the heap's: threads are boxes, and making one reserves room for it in the ready, blocked and dead queues first. Making a thread can fail, with `Error::NoMemory`, and is apart from starting it, which can't: `thread::new_user` gives a `thread::Unstarted` that holds the stack and the room, which dropping it gives back, and `Unstarted::start` readies it with its argument. A thread can't free the stack it runs on, so the reaper frees the threads that exit, unmapping the stack `Platform::into_stack` takes back from each one's context: a kernel thread like any other, which parks until the scheduler, filing a thread as dead, unparks it. It frees with interrupts on, and a tick that preempts it while it holds the frame, page-table or heap lock puts it back in the ready queue. The idle thread takes no lock, since a preempted idle thread runs again only once every other thread blocks or dies. A kernel-space address is never mapped again, so a dead thread's stack addresses stay unmapped. The arch crate tracks the running thread's stack, which bounds backtraces and is what `Platform::guard_page` is under, and keeps its top in TSS.RSP0, where a trap from user code starts. A new thread starts with interrupts off, which the kernel turns on once it has filed the thread that switched to it. A user thread holds its address space in an `Arc`, which its process holds too, and every switch loads the next thread's space, or the kernel's tables for a thread without one through `Platform::activate_kernel_tables`. Neither takes a lock, since a tick switches inside the trap handler: a space's `activate` takes `&self`, and the reference the thread holds keeps its tables alive. The kernel's `paging::Space` destroys its address space when it drops, so whichever lets go last destroys it: the reaper, or the last handle to a process that never started.

Until its drainer runs, the logger draws each record as it comes, holding the sinks' lock with interrupts off, so an interrupt handler can log: the code it interrupted can't be holding the lock. `kernel::init` starts the drainer last, a kernel thread like the reaper, and from its first run on, records go into a 128 KiB ring, which `lib/logring` keeps, with host tests under Miri. A kernel record is formatted into 512 bytes on the stack with no lock held, cut short with `...` past that, then copied into the ring with interrupts off. One that doesn't fit is dropped and counted, and the drainer logs the count. A user write's lines go in together once there is room for all of them; until then its thread waits on a list, taken with interrupts on, with the room its write needs, and after every piece it draws the drainer wakes only the waiters that now fit. The logger unparks the drainer after each record, so nothing may log while holding the scheduler's lock. The drainer takes up to 32 bytes at a time, never splitting a character, and draws them to both sinks holding their lock with interrupts off: about 2.8 ms of serial at 115200 baud, plus a console scroll when a newline is among them. So interrupts wait at most one piece, timer ticks that come meanwhile count as one, and a panic or the test summary on another thread finds the sinks free. A panic's report and the test summary first draw what is left in the ring, unless the ring is locked because the panic came from code holding it. An exception, NMI or machine check inside the drainer's draw can still find the sinks' lock held, and the panic path's `try_lock_unlisted` covers that, as before. A hang with interrupts off loses what is still in the ring, since the drainer never runs again and no watchdog tick comes.

## User mode

User code runs in a thread of its own, which `thread::spawn_user` starts with an address space, an entry point, a stack pointer and one argument. The thread switches to the space like any other, then leaves for ring 3 through `Cpu::enter_user`, an IRETQ with every general register but the argument's zeroed and only IF set in RFLAGS. What the thread had on its kernel stack is gone after that: every trap from ring 3 starts at the stack's top. A user thread also belongs to a process (see Processes). A process has one thread until a later item adds more, so a thread, its space and its process end together.

User code calls the kernel with SYSCALL, by ADR [0007](adr/0007-syscall-abi-x86_64.md)'s convention, with numbers and error codes from `thisos-abi`. The kernel runs on one CPU until the SMP milestone gives each CPU its own state, so the SYSCALL stub uses no SWAPGS: it parks the user's stack pointer in a static and loads the stack top from TSS.RSP0. It then pushes the same frame an IDT stub does, with RCX as RIP, R11 as RFLAGS and a vector of its own, 0x100, and calls the same handler, as `Trap::Syscall`, so a syscall can switch threads or end the thread as a tick or a fault can. SFMASK clears IF, DF, TF, AC, NT and IOPL on entry, and the handler asserts that IF, DF, TF, AC and NT are clear when a syscall reaches it; a ring-3 test sets DF, AC and NT before its syscall. The kernel turns interrupts on for the syscall's body, so a syscall may allocate and free, and a tick may preempt it, leaving its frame on the thread's own kernel stack. A syscall returns through SYSRET, after the arch crate checks that RIP is no higher than user space's end, which a `syscall` in the last bytes of user space returns to and which is canonical, with interrupts turned off before the stack pointer goes back to the user's. `exit(status)` ends the calling process, and `write(buf, len)` logs up to 1 KiB of UTF-8 text as info records with target `user`, one per line, a newline at its end dropped; `close`, `duplicate` and `restrict` work on handles (see Handles), `memory_create`, `map`, `unmap`, `memory_read` and `memory_write` on memory objects (see Memory objects), `channel_create`, `send` and `receive` on channels (see IPC), and `process_create`, `map_into`, `process_start` and `process_end` on processes (see Processes). A number the kernel doesn't know returns `Error::UnknownSyscall`. `write` copies the text into a buffer on the kernel stack and fails without writing anything with `Error::TooLong`, `Error::BadAddress` or `Error::NotUtf8`. It waits while the log's ring has no room for all its lines, and fails with `Error::NoMemory` if the heap has no room to list it among the waiters. Other control characters show as escapes such as `\u{1b}`, so user text can't start a line that reads as the kernel's or move the terminal's cursor. A zero-length write reads nothing, checks no address and logs one empty line, which `println!()` relies on. The copy is `Platform::copy_from_user`, which takes bytes inside one page, walks the active space's tables, checks that the page is mapped for user code, and reads its frame through the kernel's mapping of physical memory, so SMAP never opens and a bad address returns an error instead of faulting; it panics on bytes that cross a page. The kernel splits each copy at page boundaries and calls it once a page with interrupts off, so with one CPU nothing else runs to unmap or write a page while it is read. `Platform::copy_to_user` writes the same way, and also needs the page writable.

`TrapFrame::raised_by_user` tells the kernel's handler that user code raised a trap: a syscall, or an exception from ring 3 that isn't an NMI, a machine check or a double fault. Any such trap but a syscall ends the thread and its process, with a warning naming the trap and the instruction; a page fault, a privileged instruction, a breakpoint, a debug exception and an x87 or SIMD instruction all do. The handler ends the thread with interrupts still off: a #DB comes in on its IST stack, where the next #DB starts again at the top, so a tick there would let another user thread's #DB overwrite the dying one's frames. The reaper frees it. The kernel saves no x87, SSE or AVX state, so it turns all three off ([0007](adr/0007-syscall-abi-x86_64.md)).

Programs are crates under `user/`, built for the kernel's target, `x86_64-unknown-none` or `aarch64-unknown-none-softfloat`, and so soft-float. Each links `thisos-rt`, the one user crate allowed unsafe code, which has the entry point, the syscall wrappers and the panic handler, and names its main function, a `fn(Handle<Channel>) -> u64`, with `thisos_rt::entry!`. `_start` calls it with the handle its creator started it with, in its argument, and passes its result to `exit`. `thisos_rt::Handle<T>` isn't `Copy` and closes its handle when it drops, and has `duplicate` and `restrict`; `T` is one of the uninhabited markers `Process`, `Memory`, `Channel` and `Unknown`. `Handle<Memory>::create`, `Handle<Channel>::create` and `Handle<Process>::create` make objects. `Handle<Memory>` has `read` and `write`, `Handle<Channel>` `send` and `receive`, and `Handle<Process>` `map_into`, `start`, which hands the start handle back if it fails, and `exit_status`; every handle has `wait`, a wait on its object alone. `thisos_rt::wait` takes a slice of `WaitItem`s, each borrowing a handle, and an `Option<Duration>`, `None` waiting for good. A message's handles are `Handle<Unknown>`: `into_unknown` erases a type and `cast` claims one without a syscall, which is memory-safe, since the kernel checks the object's type on every call and answers a wrong claim with `Error::WrongType`. `send` hands the handles back if it fails. `receive` takes a `Vec<u8>` that it grows to 64 KiB, so a loop reusing it allocates once. `print!` and `println!` format each call into a 1 KiB buffer on the stack and write a record at each newline, without the newline, and one for what is left at the end of the call. A longer line goes out in pieces, split between characters, and a full buffer waits for more of its line before it goes, so a 1 KiB line and its newline make one record. A panic writes its location and message, cut to 1 KiB, and exits with status 101, Rust's own exit code for one; a panic while formatting that message exits at once. `thisos-rt` is the global allocator: talc, over memory objects it maps one after another from `0x4000_0000` whenever talc runs out, each 64 KiB or the request rounded up to pages, whichever is more. It closes each object's handle once the object is mapped, and never unmaps. That heap's base is the one integer `thisos-rt` turns into a pointer. Programs link at a fixed address with `--no-pie`, at lld's default base of `0x20_0000`, so loaders load them without relocating them. The loader's ramdisk is a POSIX ustar archive of regular files named by program: `init`, `hello`, `fault`, `ping`, `pong` and `checks`, which xtask builds in the kernel's profile and puts in every image of either architecture, test images included: `bootloader` loads x86_64's as its ramdisk, and Limine aarch64's as its one module. `lib/ustar` reads it, with host tests under Miri: the kernel finds `init` in it, and `init` parses it one header at a time through `memory_read`. `BootInfo::ramdisk` hands it to the kernel, which logs its size and, once it has frames and a heap, copies it into a memory object, since the loader's memory isn't the frame allocator's to share; the loader's copy stays where it is.

The kernel's main function loads `init` and starts it before it exits into the idle thread, and panics if it doesn't start, since a bad `init` or ramdisk is a build bug. `lib/elf` checks the file once: a little-endian ELF64 executable for the machine `Platform::ELF_MACHINE` names, with no dynamic, interpreter or TLS segment, its load segments inside the file, in order of address and on pages of their own, none both writable and executable, and the entry point in an executable one. The kernel copies each page of each segment into a new frame with `Platform::fill_frame`, which writes the file's bytes for that page and zeroes the rest, `.bss` included, and maps it read-only, read-write or read-execute. The stack is 64 KiB of zeroed pages ending where user space ends, `thisos_abi::USER_SPACE_END`, `0x7fff_ffff_f000`, which the kernel checks against the HAL's when it loads `init`, and an overflow runs into unmapped memory. `init` starts as any process does (see Processes), with the stack pointer at the stack's top and one handle: the receiving end of a channel whose other end the kernel closed, where one message waits, carrying a handle to `init`'s own process, with read, write, duplicate and transfer, and one to the ramdisk's memory object, with read, duplicate and transfer. When it exits the kernel logs the status, as for any user process, and idles.

Tests that need user code with exact registers run code the arch crate writes: `thisos_hal::UserProgram` names fourteen small programs, which `Platform::write_user_program` copies into a frame, as `Probe` names the kernel's trapping code. Tests that can go through `thisos-rt` run a program from the ramdisk instead, as `checks` does.

## aarch64

The aarch64 crate implements the same HAL as x86_64's, under QEMU's virt machine with a `cortex-a76` CPU ([0006](adr/0006-aarch64-behind-x86_64.md)). Where it differs:

- **Page tables.** TTBR1 holds the kernel's upper half, and a user space's level 0 table goes in TTBR0, with 4 KiB pages and 48-bit addresses. `take_page_tables` copies Limine's upper half as on x86_64, and makes every leaf global, out of EL0's reach and PXN, except the read-only leaves inside the kernel's `.text`. It reserves a free level 0 entry for the heap and kernel space as x86_64 reserves a level 4 entry. Every space uses ASID 0 and user pages are not global, so a switch writes TTBR0 and drops ASID 0's TLB entries. While no user space is active, `TCR_EL1.EPD0` turns TTBR0's walks off. The kernel sets the Access flag itself and leaves `TCR_EL1.HA` and HD off, so the walker never writes the tables. PAN is on from boot, and the kernel panics on a CPU without it. Once on its own tables the kernel writes all of `SCTLR_EL1` from `thisos_arch_aarch64::SCTLR`, logging what the loader left there, so that no bit the loader set reaches EL0: EL0 writes to DAIF, cache maintenance, WFI and WFE trap and end the program, and WXN makes every writable page execute-never. User space ends at `thisos_abi::USER_SPACE_END`, as on x86_64. Mapping a user page read-execute first cleans its frame's data cache lines through the physical-memory mapping and invalidates the instruction caches, so that user code never runs bytes a frame held before; W^X means no page is written while it is executable. The framebuffer is normal non-cacheable memory, MAIR attribute 2, which gathers stores as write-combining does.
- **Traps.** `VBAR_EL1` points at a table of 16 entries that save the registers, ESR, FAR and the entry's number in one frame. The CPU pushes nothing on a trap, so a full stack can't fault the way it does on x86_64: each entry instead checks, as Linux does, that the frame fits on the stack, which works because every stack EL1 runs on is 64 KiB with its start aligned to 128 KiB. `map_stack` maps that size only, and panics on any other. An entry that finds it doesn't fit moves to a 64 KiB overflow stack with a guard page, and the kernel sees `Trap::DoubleFault`. Only translation, access flag and permission faults are page faults; other synchronous exceptions are `Trap::Other` with the exception class and ESR. A breakpoint resumes after its `brk`. The frame holds `SP_EL0` too, since a tick may switch to another user thread inside the handler, and the handler returns to EL1 and EL0 alike; traps from EL1 on SP_EL0, SErrors and FIQs are reported, and an entry the kernel can't resume from panics, naming the entry, if the handler returns, as it does for a spurious FIQ. The kernel masks interrupts once the handler returns, since a syscall turns them on, and one taken between the restore of `ELR_EL1` and `SPSR_EL1` and the `eret` would overwrite them.
- **Devices.** The kernel finds the GICv3 and the virtual timer's interrupt in the device tree, and maps the distributor and the boot CPU's redistributor as Device-nGnRE memory, MAIR attribute 3, in its copy of the physical-memory mapping. Only the timer's interrupt is enabled. The tick is the virtual timer, CNTV, at 100 Hz from `CNTFRQ_EL0`, each tick moving its compare value one period on, so that the handler's latency adds no drift; ticks missed while interrupts are off count as one. `Platform::timer_frequencies` reports nothing, since the virt machine has no second clock fine enough to check `CNTFRQ_EL0` against. A test run ends through semihosting's `SYS_EXIT_EXTENDED`, only when the device tree's root is QEMU's.
- **Threads.** A suspended thread's x19-x30 and `TPIDR_EL0` sit on its own stack. `TPIDR_EL0` goes with the thread, since EL0 can write it and would otherwise read what another process left there. The arch crate moves the timer's compare value on, which lowers its interrupt, and ends the interrupt before it calls the handler, as x86_64 sends its EOI. `Cpu::wait_for_interrupt` masks interrupts around its `wfi`, which a pending interrupt ends whether masked or not, so one that comes before the `wfi` isn't missed.
- **User mode.** A syscall is `svc #0` with the number in x8 and the arguments in x0 to x5, giving the error in x0 and the value in x1 ([0010](adr/0010-syscall-abi-aarch64.md)); any other `svc` ends the thread. `Cpu::enter_user` moves SP to the top of the thread's stack, where the next trap from EL0 starts, and `eret`s to EL0t with IRQs, SErrors and debug exceptions unmasked; FIQs stay masked, as at EL1, since group 0, which signals them, is never enabled. `CPACR_EL1.FPEN` traps FP and SIMD at EL0 and EL1, and `CNTKCTL_EL1.EL0VCTEN` lets user code read the virtual counter, which `thisos_rt::cycles` reads, at the frequency in `CNTFRQ_EL0`. A user `brk` is a breakpoint, which ends the thread like any other user trap. `TPIDRRO_EL0`, which user code can read, stays 0: boot clears it, and the trap entries' overflow path, which parks x0 there for want of a free register, clears it once it has x0 back, keeping the frame's address in `TPIDR_EL1`. `Platform::raise_spurious` has no `int` to use, so it masks interrupts, sets `ELR_EL1` and `SPSR_EL1` as an IRQ would, and branches to the IRQ entry, where the GIC answers 1023 with nothing pending. A test enters the FIQ entry the same way, through the arch crate's `raise_spurious_fiq`, and expects that panic. The test programs are aarch64 assembly; `Spin` counts 2^24 ticks of the 62.5 MHz counter.
- **Not there yet.** There is no serial port, so the kernel logs to the framebuffer alone, and CI, which runs aarch64's QEMU tests, reports a failure there only by QEMU's exit status. Its `paging.rs` runs on the host and under Miri, over a fake CPU, as x86_64's does.

## Handles

Kernel objects are reached through typed handles ([0002](adr/0002-handles.md)). Each handle names one object of a fixed type, such as a channel, memory object, thread, process or interrupt.

A handle carries rights from a fixed set: read, write, execute (memory objects only), duplicate and transfer. Rights can be removed and never added. Sending a handle over a channel moves it out of the sender. The kernel has no global names: a process reaches an object only through a handle it was given. In user-space Rust, a handle is a non-`Copy` `Handle<T>`, such as `Handle<Channel>`, that closes on drop.

A handle is a `u32` naming a slot in its process's table: the slot's index in the low 16 bits and the slot's generation in the high 16. Generations start at 1, so 0 is never a handle, and closing a handle bumps its slot's generation, so a stale handle fails with `Error::BadHandle` instead of naming whatever took the slot. A slot whose generation would wrap is retired. The table grows as handles are made, up to 65536 slots, and reuses closed ones; a full table fails with `Error::NoHandles`. The table is `lib/handles`, generic over what it holds; the kernel's objects are `enum Object`, one variant per type, each an `Arc`, and the table's lock is a spin lock that trap handlers never take. Rights are `thisos_abi::Rights`, a bit set. `close(h)` closes a handle. `duplicate(h, rights)` makes a new handle to h's object, needs the duplicate right (`Error::AccessDenied` without it), and gives only rights h has (`Error::BadRights` otherwise). `restrict(h, rights)` leaves h with only `rights`, which must be ones it has, and needs no right.

## Memory objects

A memory object is zeroed frames, a fixed number of them, all taken when it is made ([0008](adr/0008-memory-objects.md)). `memory_create(size)` makes one of `size` bytes and returns a handle with every right. `map(h, offset, len, addr, rights)` maps `len` bytes of h's object from `offset` at `addr` in the caller's space, where the caller chose `addr`; `rights` is read, read and write, or read and execute, and h must have them. Sizes, offsets, lengths and addresses are multiples of 4096. `unmap(addr)` removes the whole mapping that starts at `addr`; there are no partial unmaps. A mapping holds its object, so closing the last handle frees nothing while the object is mapped, and an object frees its frames when its last handle and mapping are gone. The errors are `Error::OutOfRange` for a zero or unaligned size or length, or a range past the object's end, `Error::BadAddress` for an unaligned offset or address or a range outside user space, `Error::AddressInUse` for a range that overlaps a mapping, `Error::NoMemory`, `Error::WrongType` for a handle to another kind of object, and `Error::Conflict` for a mapping that would make an object writable and executable at once: an object mapped writable anywhere can't be mapped executable, and the reverse, so double mapping can't get around W^X. `memory_read(h, offset, buf, len)` and `memory_write(h, offset, buf, len)` copy between the caller and an object at any byte offset, a page or less at a time through the HAL's `read_frame` and `write_frame` with interrupts off, and need read and write; a range past the object's end fails with `Error::OutOfRange`, and a bad buffer with `Error::BadAddress`, after the pages before it. `memory_write` fails with `Error::Conflict` while the object is mapped executable anywhere, and holds the object's counts' lock until it is done, so no executable mapping starts meanwhile. A loader fills an object with `memory_write`, or through a writable mapping it unmaps, then maps it executable.

Every user page belongs to a memory object, init's segments and stack included: the kernel's loader makes one object per segment and one for the stack. The HAL's `AddressSpace<O>` maps an object's frames and holds the `O`, the kernel's `Mapping`, an `Arc` of the object that counts toward its writable or executable mappings until it drops. The space hands the `O` back from `unmap` or `destroy` only once no page maps its frames, so the types keep a frame from being freed while user code reaches it. Its region list, ranges that never overlap, and the counts are `lib/regions`, with host tests under Miri. `map` and `unmap` take `&self` and a spin lock of the space's own, and the kernel writes an object's frames through a `&mut Frame` only while it holds the object alone, before it is shared or mapped; `write_frame` takes a `&Frame`, since no Rust reference into a frame's bytes exists outside `fill_frame`.

## IPC

Processes talk through kernel-buffered, bounded, two-way channels that carry bytes and handles. A thread can wait on several objects at once. Bulk data goes through shared memory objects. Milestone 4's round-trip measurement on the laptop confirmed this ([0003](adr/0003-ipc-channels.md)), which records the numbers: a 16-byte round trip takes 1.7 µs and a 64 KiB one 8.7 µs.

`channel_create()` makes two endpoints and returns both handles in one value, the first in the low 32 bits. Each handle has read, write and transfer, and no duplicate, so an endpoint has exactly one handle and one reader. `send(h, bytes, len, handles, count)` needs write and queues a message of at most 64 KiB and 64 handles (`Error::TooLong` beyond either) at the other endpoint, which holds at most 64 messages. A full queue fails the send with `Error::ShouldWait`, and so does `receive` on an empty one: nothing in a channel call blocks, and the wait call is how a thread waits for room or a message. Every handle a message carries needs transfer and moves out of the sender's table with its rights, all of them or none: a bad handle, one named twice (`Error::BadHandle`), one without transfer (`Error::AccessDenied`), or either endpoint of the channel it goes over (`Error::Cycle`) sends nothing. `receive(h, bytes, len, handles, count)` needs read and returns the byte count in the low 32 bits of its value and the handle count in the high 32; buffers too small fail with `Error::BufferTooSmall`, whose value holds the message's two counts in the same way, so that a receiver with a small buffer learns what it needs; every other error's value is 0. `thisos-rt`'s `receive_into` reports those counts as `ReceiveError::TooSmall`, and its `receive` tries the `Vec`'s capacity first and grows it to the message's size if that is too little. A failed receive, for that or a bad buffer or a full handle table, leaves the message queued: the kernel holds the channel's lock across the handle inserts and the user copies, and takes the inserts back on failure. Once an endpoint closes, a send to it fails with `Error::PeerClosed`, and its peer still receives what was queued before failing the same way.

The queues and closed flags are `lib/channels`, generic over what a message carries, with host tests under Miri. The kernel's two endpoints share one `Channel` behind one spin lock, taken with interrupts on and before the calling process's handle-table lock, so a send and its peer's close never race. An endpoint closes when its last hold goes: its handle, or the message carrying it. Closing leaves what waited there queued, and the endpoint's drop takes it one message at a time and drops its objects after the lock. Endpoints in those messages that nothing else holds close in turn and go on a stack linked through the `Arc`s that held them, whose queues drain in the same loop, so a chain of channels queued inside each other, as long as user code made it, drops at a constant stack depth, and closing allocates nothing. A cycle across two or more channels, A's endpoint queued at B and B's at A with no handle left to either, is never dropped; refusing an endpoint over its own channel only stops the shortest one.

`wait(items, count, timeout)` blocks until one of at most 64 objects has a signal its item asks for. An item is three little-endian `u32`s: a handle, which needs read, the wanted signals, and the observed ones, which a successful wait writes for every item; its value is the number of items with a wanted signal. Signals are states, so a wait returns at once for one already set and nothing consumes them. Endpoints have three: readable while a message waits there, writable while the peer is open and has room, and peer-closed. A process has one, ended (see Processes). Items the call can't both read and write fail with `Error::BadAddress`, another object's handle with `Error::WrongType`, and a wanted set that is empty or holds a signal its object never has, `Signals::ENDPOINT` or `Signals::PROCESS`, with `Error::BadSignals`, since the call would otherwise wait out its timeout for nothing, all before the call blocks; it finds out whether it can write the items by writing them back unchanged. The timeout is in nanoseconds and rounds up to whole ticks, plus one for the tick under way, so a wait lasts at least that long: 0 only checks, `u64::MAX` waits for good, and once it passes the call fails with `Error::TimedOut`. No items makes it a sleep, and no items with `u64::MAX` fails with `Error::BadSignals` before it blocks, since nothing could end it and no call ends another process. Each side of a channel keeps the ids of the threads waiting on it, in `lib/channels`: the waiting thread adds its id to every item's list, checks the signals, parks, and takes its id off every list before it checks again, so a wake that lands between the check and the park makes the park return at once. A send, receive or close drains the list of each side that gained a signal and unparks those threads under the channel's lock, so the list keeps its room and the next wait doesn't allocate it again; the scheduler's lock is taken inside the channel's, and nothing takes them the other way round. A thread woken for nothing it wants waits again in the kernel, so user code never sees a spurious return. A wait holds the objects its handles named, so closing a handle during a wait wouldn't end it; with one thread a process, nothing can close one then yet.

## Processes

A process has a handle table, an address space and, once it ends, how it ended: its exit status, or the trap that killed it. Its threads hold it, as do the handles that name it. User space builds processes ([0004](adr/0004-process-creation.md), [0009](adr/0009-process-building.md)); the kernel builds only `init`, the same way.

`process_create()` makes a process with an empty address space and no thread, and returns a handle with read, write, duplicate and transfer. `map_into(process, memory, offset, len, addr, rights)` maps into its space as `map` maps into the caller's, with the same errors. `process_start(process, ip, sp, handle)` makes its one thread at `ip` with stack pointer `sp`, which must be in user space (`sp` may be at its end; `Error::BadAddress` otherwise), and moves `handle`, which needs transfer, into its table, where the thread gets it as its argument. Both need write on the process handle, and once the process has started both fail with `Error::Started`: only a process's own threads change its space while it runs. `process_start` does everything that can fail, the thread's stack and the table's room included, before it takes the handle out of the caller's table, so a failed start leaves the caller's handle where it was. By convention the start handle is a channel endpoint, over which the creator sends the rest: `init`'s loader sends `hello` its line that way.

`exit` ends the process, and a process also ends when its last thread ends. The reaper closes every handle in the table when it frees that thread, within a round of the thread's end even while other threads stay ready, which also breaks the cycle a handle to itself makes, then lets go of the space after the thread's own hold, which destroys it. Only then does the process's handle have `Signals::ENDED`, which stays set, so a waiter that wakes finds the process's memory free; the trap handler that kills a process wakes nobody. `process_end(h)` needs read and returns the exit status once the process has ended, fails with `Error::Killed` if a trap ended it, and with `Error::ShouldWait` before then. The process object lives on while some handle names it. A process that never starts has no handles in its table, so its last handle's close frees it and its space at once.

`init` holds the first loader, in `user/init/src/loader.rs`: it reads a program from the ramdisk, checks it with `lib/elf`, makes one memory object per segment, writes the file's bytes in with `memory_write` and maps it into the new process with its segment's rights, then maps a 64 KiB stack under `USER_SPACE_END` and starts the process with one handle. `init` starts `hello` and sends it `world`, starts `fault`, whose stack overflow the kernel kills it for, and starts `ping` and `pong`, which share one channel: `pong` starts with its end, and `ping` with a channel to `init`, which sends `ping` its end over it. `ping` times 1000 calls of `thisos_rt::null_syscall`, a close of handle 0, and 1000 round trips each of 16 bytes, 1 KiB, 4 KiB, 64 KiB, and 16 bytes with a memory object's handle, after 100 of each that it doesn't count, which `pong` sends back until `ping` closes its end. It reads the time with `thisos_rt::cycles` and its frequency with `cycles_hz`: on x86_64 RDTSC, which works in ring 3 since the kernel leaves CR4.TSD clear, and CPUID leaf 0x15, which QEMU without KVM doesn't give; on aarch64 `CNTVCT_EL0` and `CNTFRQ_EL0`. It sends `init` each one's minimum, median and maximum, which `init` prints in cycles, and in nanoseconds where the frequency is known. Then `init` waits for each program to end and prints one line with every end: `hello`'s exit status, the line's length, that `fault` was killed, and `ping`'s and `pong`'s status.

## User-space drivers

Drivers and services contain no unsafe code. MMIO, port I/O and DMA buffers go through one audited crate with safe, typed APIs. Until the IOMMU is used, a driver that can program a device's DMA can still reach any physical memory, so drivers with DMA are trusted that far.

## Milestones

Each milestone ends with QEMU and the laptop doing something they couldn't before.

1. **Boot.** The workspaces and xtask; the kernel boots under OVMF and on the laptop; serial and framebuffer logging; the panic handler; QEMU tests; CI passing.
2. **Kernel core.** GDT, TSS and IDT; exceptions with trap frames; a frame allocator built from the memory map; page tables owned by the kernel; the heap; the LAPIC timer.
3. **User mode.** Address spaces, threads, context switching, preemptive round-robin scheduling and syscall entry. `init` loads from the ramdisk, prints through a syscall and exits.
4. **Handles and IPC.** The per-process handle table, channels that carry handles, shared memory and a wait call. The page-table code's raw-pointer walks run under Miri on the host, over a buffer standing in for physical memory. A log that a kernel thread draws from a ring once the kernel is up, so that code that logs doesn't wait for the serial port with interrupts off. `init` starts two processes that talk to each other.
5. **User-space drivers.** Interrupts delivered to user space; handles for MMIO and I/O port ranges; serial and i8042 keyboard drivers in user space; a shell that runs programs from the ramdisk.
6. **Storage.** PCI enumeration in user space, an NVMe driver, a filesystem server and a namespace protocol.
7. **std.** A std platform-layer patch over the ABI as it stands then, giving `std::{io, fs, env, process, thread, time}`. An earlier spike showed this route works.

Between milestones 4 and 5, a milestone of its own, **SMP on x86_64**, runs the kernel on every core, so that milestone 5's interrupt delivery and device handles are built for several CPUs from the start. Application processors start from the ACPI MADT; each CPU gets its own trap state, run queue and timer; one big kernel lock, taken on every kernel entry, covers what the existing object locks don't, and is to be removed path by path where measurements on the laptop show contention; kernel mappings are shot down across CPUs. It ends with `init`'s programs spread over every CPU and IPC round trips measured on one CPU and across two. aarch64 stays on one CPU (see Non-goals).
